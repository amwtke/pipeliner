# 压测报告

这一页记录示例应用（净需求计算）在三档数据量下的实测结果，以及从中看到的瓶颈。读者是想评估 pipeliner 能扛多大数据量、该怎么调优的人。

测试日期 2026-11-14，代码版本 `28bef89`。

## 结论

- **结果正确。** 7 个场景全部成功。同一档数据在不同 pod 数、不同执行模式、不同控制面下，校验和完全一致，结果表里没有重复行。所有 pod 的日志里 ERROR 和 WARN 都是 0，没有死信，没有 chunk 重试。
- **4 万物料（每阶段约 320 万行）用 6 个 pod 跑完一轮需要 200 到 227 秒**，数据库跑在一台 4 核虚拟机里。
- **Redis 内存峰值 59 MB。** 背压把通道积压限制在水位线附近，Redis 占用与数据总量基本无关。
- **瓶颈不在框架的传输上，而在一个切分太粗的 pipeline 上。** `cap-alloc` 只能切成 3 份，占了总耗时的三分之二。
- **控制面用 Redis 还是 MySQL，耗时相差约 2%。**

## 测试环境

这是一台开发笔记本上的测试，数据库的资源被刻意压得很低。数字适合用来看趋势和找瓶颈，不代表生产环境的绝对性能。

| 项 | 配置 |
| --- | --- |
| 宿主机 | 一台笔记本，48 GB 内存。pod 直接跑在宿主机上 |
| pod | 每个 pod 一个 JVM，`-Xms512m -Xmx4g` |
| 数据库 | Redis、MySQL 8.4、ClickHouse 装在同一台 4 核的 Linux 虚拟机里 |
| MySQL | 低资源配置：InnoDB 缓冲池 128 MB，关闭 performance_schema 和 binlog |
| ClickHouse | 低资源配置：服务内存上限 1.5 GB |
| 框架参数 | 水位 64 / 32，master 每 500 毫秒推进一次，其余为示例应用的默认值 |

虚拟机与其他实验共用。每个场景前后都记录了虚拟机负载，测试期间没有来自其他进程的明显干扰（1 分钟负载最高 2.6，基本都是测试自身产生的）。

## 负载

示例的净需求计算图有 8 个 pipeline，规划成 6 个 run：

| run | pipeline | 模式 | 做什么 |
| --- | --- | --- | --- |
| R1 | algo-submit | INLINE | 把物料提交给模拟的外部算法，等回调 |
| R2 | gd-fix → big-net → core-grade | CLUSTER | 读毛需求，修正，大件净算，分级。三个 pipeline 流式相连 |
| R3 | cap-alloc | LOCAL | 按站点分配翻新产能 |
| R4 | big-final | CLUSTER | 大件最终净需求 |
| R5 | fine-net | CLUSTER | 细料净需求 |
| R6 | publish | INLINE | 汇总发布 |

数据按物料数生成：每个物料 80 行（5 个节点 × 16 个月），40% 是大件，60% 是细料。所以 4 万物料对应每个阶段约 320 万行。所有场景使用同一个随机种子，同一档数据的结果可以直接比较。

## 正确性

| 检查 | 结果 |
| --- | --- |
| 同一档数据的校验和 | L2a、L2b、L2m 三者完全一致；L3a、L3b、L3c 三者完全一致 |
| 结果表重复行 | 0。1.2 万档 96 万行，4 万档 320 万行，行数与按业务键去重后的行数相等 |
| round 状态 | 7 个场景全部 `SUCCEEDED` |
| pod 日志 | ERROR 0 条，WARN 0 条 |
| 死信、chunk 重试 | 都是 0 |
| master 切换 | 每个场景只有启动时的 1 次选主 |

校验和是对结果表每一行的业务列做与顺序无关的哈希，再加上行数和数量合计。pod 数从 3 变成 6、`cap-alloc` 从单 pod 变成多 pod、控制面从 Redis 换成 MySQL，算出来的每一行都相同。

## 分析

### 1. cap-alloc 占了三分之二的时间，加 pod 没有用

这是最大的瓶颈，而且原因很清楚。

`cap-alloc` 按站点切分数据，示例里只有 3 个站点，所以只有 3 个 split，也就只有 3 个 chunk。4 万物料时每个 chunk 约 107 万行：

| 物料数 | 单个 chunk 的平均处理时间 | 最长 |
| ---: | ---: | ---: |
| 3,000 | 4.1 秒 | |
| 12,000 | 16.1 秒 | 29.5 秒 |
| 40,000 | 53.1 秒 | 96.2 秒 |

后果有三个：

- **并行度被锁死在 3。** 换成 CLUSTER 模式、让 3 个 chunk 分到不同 pod 上（L3b），也只快了 16%（160.9 秒降到 134.4 秒）。这时虚拟机里的 MySQL 和 ClickHouse 峰值各占约 3 个核，成了新的限制。
- **内存吃紧。** 一个 split 会被整个读进内存。L3b 里 pod 的常驻内存峰值到了 4.0 GB，堆上限正是 4 GB。数据再大就会 OOM。
- **pod 数不影响它。** 3 个 pod 和 6 个 pod 下它的耗时一样（160.7 秒和 160.9 秒）。

这不是框架传输能力的问题，而是这个 pipeline 的切分键选得太粗。改法见 [改进方向](#改进方向)。

> [!NOTE]
> L2b（6 个 pod）的整轮耗时反而比 L2a（3 个 pod）长 7 秒，差在 `cap-alloc` 上：60.5 秒对 49.2 秒。`cap-alloc` 在这两个场景里的执行方式完全相同，理论上不该有差别。原因没有查明，推测是共享虚拟机里数据库状态的波动。4 万物料那一档没有出现这个现象。

### 2. R2 的流式链路：超过 3 个 pod 之后，加速被数据库卡住

pod 从 3 个加到 6 个：

| 物料数 | R2 耗时（3 pod → 6 pod） | 加速比 |
| ---: | --- | ---: |
| 12,000 | 20.2 秒 → 14.5 秒 | 1.39 |
| 40,000 | 60.3 秒 → 44.2 秒 | 1.36 |

pod 数翻倍只快了不到 1.4 倍。`gd-fix` 的吞吐在 6 个 pod 时停在每秒 7.5 万行左右，1.2 万物料和 4 万物料下都是这个数，说明到顶了。限制来自那台 4 核的虚拟机：三个数据库共用 4 个核，而 R2 同时在读 ClickHouse、写 ClickHouse、写 MySQL。

链路内部，最慢的是末端的 `core-grade`（每秒 1.7 万到 2.9 万行）。证据是 `BUSY` 等待时间：

| 场景 | big-net 累计等待 | gd-fix 累计等待 |
| --- | ---: | ---: |
| L2a | 96.7 秒 | 12.4 秒 |
| L2b | 105.7 秒 | 20.7 秒 |
| L3a | 317.4 秒 | 107.2 秒 |
| L3c | 309.6 秒 | 65.0 秒 |

这是各线程等待时间的合计。`big-net` 等得最久，说明它算好的结果经常写不进下游：下游的 `core-grade` 消费不过来。压力再从 `big-net` 传给 `gd-fix`。这正是背压在按设计工作（见 [背压与流控](./backpressure.md#43-压力逐跳回传)）。

### 3. 通道长度超过了高水位，但这是预期行为

高水位是 64，而 `gd-fix` 到 `big-net` 的通道峰值到了 88 到 150。

原因是水位检查发生在提交之前，而一次提交会把一个输入的全部输出一起写入。`gd-fix` 是读库的 pipeline，它的一个 split 就是一次提交：

| 物料数 | 一个 split 输出到这条通道的行数 | 切成的 chunk 数 | 理论上限（64 + chunk 数） | 实测峰值 |
| ---: | ---: | ---: | ---: | ---: |
| 12,000 | 2.4 万 | 30 | 94 | 88 到 89 |
| 40,000 | 8 万 | 100 | 164 | 138 到 150 |

实测值都落在理论上限之内。Redis 内存峰值只有 59 MB，背压是有效的。如果希望积压更贴近水位线，把 split 切细即可（见 [背压与流控](./backpressure.md#44-高水位是软上限)）。

### 4. master 偶尔有一次推进很慢

master 每次推进的平均耗时只有十几毫秒，但最长的一次随数据量明显增长：

| 物料数 | 最长的一次推进 |
| ---: | ---: |
| 3,000 | 0.10 秒 |
| 12,000 | 0.51 秒 |
| 40,000 | 2.37 秒 |

很可能的原因是示例里的 `conserve-check` 闸门：它的判定函数在 master 的推进线程上同步执行，对 320 万行的结果表做两次 `count(*)`。这个闸门在 4 万物料时的等待时间正好也是 2.4 秒左右。这一点没有单独验证。

它值得注意，是因为示例配置的租约是 6 秒，master 单次推进超过租约的一半（3 秒）就会被中止。数据量再涨一半左右，这个闸门就可能开始拖慢所有 round 的推进。

### 5. 控制面的开销可以忽略

同样的数据和 pod 数，Redis 控制面（L2b）85.1 秒，MySQL 控制面（L2m）87.0 秒，相差约 2%。选哪一种应该由灾难恢复的要求决定，不必考虑性能。

### 6. 规模增长

同样 6 个 pod，从 1.2 万物料到 4 万物料：

| | 1.2 万 | 4 万 | 倍数 |
| --- | ---: | ---: | ---: |
| 数据量 | 96 万行 | 320 万行 | 3.33 |
| 整轮耗时 | 85.1 秒 | 226.5 秒 | 2.66 |
| R2 | 14.5 秒 | 44.2 秒 | 3.05 |
| R3（cap-alloc） | 60.5 秒 | 160.9 秒 | 2.66 |
| R4（big-final） | 2.8 秒 | 9.3 秒 | 3.37 |
| Redis 内存峰值 | 32 MB | 59 MB | 1.86 |

耗时基本随数据量线性增长，Redis 内存增长远慢于数据量。

## 改进方向

按收益从大到小：

1. **把 `cap-alloc` 切细。** 代码里剩余产能是按（站点, 月份）记账的，各月份的分配互不影响，所以可以按（站点, 月份）切成 48 份，而不是按站点切成 3 份。这样它能真正分布到多个 pod 上，单个 chunk 的内存也降到原来的约十六分之一。这需要框架支持按多列组合切分，并且前提是真实业务里产能不跨月结转。
2. **把条件闸门移出 master 的推进线程，并加超时。** 避免一个慢查询拖住所有 round。
3. **大 split 分页拉取。** 让一个 split 不必整个读进内存。
4. **给自动扩并行度加指标。** 这次测试里无法判断它是否触发过。
5. **给数据库更多资源。** R2 在 6 个 pod 时已经受限于数据库所在的 4 核虚拟机。

前四项已列入 [路线图](../README.md#-路线图)。

## 如何复现

压测脚本是 `pipeliner-example/scripts/loadtest.sh`，一次跑一个场景：

```bash
cd pipeliner-example

# L1：3000 物料，3 个 pod
MATERIALS=3000 PODS=3 OUT=/tmp/lt/L1 scripts/loadtest.sh

# L3b：4 万物料，6 个 pod，cap-alloc 用 CLUSTER 模式
MATERIALS=40000 PODS=6 CAP_MODE=CLUSTER CAP_PARALLELISM=3 TIMEOUT_SEC=5400 SKIP_BUILD=1 OUT=/tmp/lt/L3b scripts/loadtest.sh

# L2m：MySQL 控制面
MATERIALS=12000 PODS=6 STORE_PROFILE=mysql-store SKIP_BUILD=1 OUT=/tmp/lt/L2m scripts/loadtest.sh
```

| 变量 | 默认 | 含义 |
| --- | --- | --- |
| `MATERIALS` | 3000 | 物料数，每个物料 80 行 |
| `PODS` | 3 | pod 数 |
| `STORE_PROFILE` | 空 | 空为 Redis 控制面，`mysql-store` 为 MySQL 控制面 |
| `CAP_MODE` · `CAP_PARALLELISM` | `LOCAL` · 3 | `cap-alloc` 的执行模式和并行度 |
| `SEED` | 42 | 造数据的随机种子 |
| `POD_XMX` | 4g | 每个 pod 的堆上限 |
| `TIMEOUT_SEC` | 1800 | 一轮的超时 |
| `OUT` | 自动生成 | 输出目录 |

脚本会造数据、启动 pod、提交一轮、在人工闸门处自动放行，结束后停掉 pod。输出目录里的 `report.json` 包含本页用到的所有数字：每个 run 和 pipeline 的耗时与行数、闸门等待时间、每 2 秒一次的 Redis 内存与通道长度采样、校验和、重复行检查、日志里的 ERROR 与 WARN 统计。
